memory-champ

A local memory service for your agents · CoALA · MCP · SQLite

A koala goes back to the same tree every day. Your agent should go back to the same context — no matter which terminal you opened it in.

The problem it solves

Every new terminal is a fresh case of amnesia

You're deep in a project. You close the window, or open a second one, or come back on Tuesday. The assistant is brilliant again — and knows nothing again.

Here's the loop that actually costs you money:

  1. You hit a gnarly bug. Forty minutes of back-and-forth. You solve it.
  2. Session ends. That reasoning lives in a transcript nobody will ever read again.
  3. New terminal, two weeks later. Same corner of the codebase.
  4. You re-explain the project. Then the constraint. Then the thing you already decided.
  5. The same bug reappears — and you pay full price to solve it a second time.

The waste isn't one wrong answer. It's the re-derivation: re-reading files you already read, re-litigating a decision you already made, rebuilding context that existed last Tuesday. Tokens spent on work that was already done once.

Without a memory

Context lives in the conversation. Close it and it's gone. Every new terminal starts on the forest floor and pays to climb back up.

With memory-champ

Context lives in one file on your disk, outside every repo. New terminal, new window, new week — the agent checks the tree first.

⚠ Being straight with you about this

memory-champ doesn't make forgetting impossible. It gives the agent a place to look and a place to write — somebody still has to call it. If nothing recalls at the start of a session and nothing remembers at the end, you get an empty database and the same Groundhog Day. The tool is half of it; the habit is the other half.

In plain English

A notebook your assistant is allowed to keep

Not a smarter model. A filing cabinet that sits beside the model — one it can search before it starts, and write to when it learns something worth keeping.

Episodic

What happened

“On the 4th we tried the deferred transaction and it deadlocked under two writers.” The diary. Events, with dates on them.

Semantic

What is true

“Every text read in this codebase passes UTF-8 explicitly.” The facts and rules that outlive any one session.

Procedural

How to do it

“The four steps that fix this build.” The playbooks — and the only kind you have to sign off before it counts.

Most “AI memory” is one undifferentiated pile of notes. Splitting it three ways matters because the three behave differently: an event is true on a date, a fact is true until it isn't, and a procedure is something an agent will actually go and do — which is exactly why the third one gets a lock on it.

Koala fact. A joey can't digest eucalyptus on its own — it inherits the gut microbes from its mother before it can eat the leaves. Procedural memory is the same idea: the know-how has to be handed over deliberately, or the next one starts from nothing.

How it runs

Four moves, over and over

The whole thing is one loop. Everything else is plumbing underneath it.

01
Recall
Before working: “what do I already know about this?” Comes back as a block sized to fit the prompt.
memory_recall
02
Act
The agent does the actual work. memory-champ isn't involved — it has no hands.
— your agent —
03
Remember
What was learned goes back in, tagged to a project so it surfaces next time.
memory_remember
04
Reflect
Later, it reads its own store, spots repeats, and proposes a playbook. Proposes.
memory_reflect

Step 4 is the one aimed straight at the repeat-bug problem. When the same fix shows up for the third time, reflection notices and drafts it as a procedure — a candidate sitting in a queue with your name on it, waiting for a yes.

Koala fact. Koalas sleep up to 20 hours a day, because eucalyptus is a terrible fuel. memory-champ has the same energy budget: it does nothing until asked, and its background daemon wakes on a schedule, tidies the store, and goes straight back to sleep.

Why terminals stop mattering

One tree per project

The store lives at ~/.memory-agent/memory.db — deliberately outside every repo. Changing folders doesn't change the memory. Separation comes from a label called scope, not from where you happen to be standing.

ScopeWhat lands in it
bluegum.apiThe payments service
manna.webThe marketing site
rivergum.crmA CRM build
tallowwood.gameThe weekend project

Name them however you like — these are gum trees because we couldn't help ourselves.

Three terminals working the payments service all pass bluegum.api, so all three see the same memory. A terminal on the weekend project passes tallowwood.game and sees none of it. That's the whole trick — and it's also the whole fragility:

⚠ Scope matching is exact, and there is no wildcard

Recalling bluegum when the records were written under bluegum.api returns nothing — not an error, just silence, which is far more expensive. Derive the scope from the project, keep the list somewhere the agent reads every session, and never invent a fresh one per session.

Koala fact. Koalas live in a home range of specific trees and come back to the same ones night after night. Wandering outside the range is how a koala gets into trouble — and a wandering scope argument is how memory gets lost.

The safety story

It can hand you a bad memory. That's the worst it can do.

Procedures need your signature — a real one

When the agent wants to teach itself a new playbook, it can only queue it. Candidates sit in a separate table that recall cannot reach, even if a query goes wrong. Approving requires an Ed25519 signature from a private key the agent doesn't have.

The agent holds the tool. You hold the key. It can relay an approval you produced; it can never manufacture one — and because the signed payload is stored verbatim, a procedure edited after approval fails the check instead of quietly staying “approved”.

Koala fact. Koalas have fingerprints so close to ours that they've reportedly muddled forensic examiners. Fitting, for the one part of this system that runs on a signature only you can produce.

What it deliberately can't do

  • No network. Ever.
  • No filesystem outside its own database.
  • No talking to a user, no sending anything anywhere.
  • No deleting by default — bytes only go away on an explicit hard delete with confirm: true.

What it does on purpose

  • Reports contradictions, never resolves them. If two memories disagree you get both — it has no basis for picking a winner.
  • Measures the context block it returns, so recall can't quietly blow your window.
  • Degrades visibly. A missing optional dependency means weaker recall that says so, not a crash and not a silent downgrade.
  • The whole memory is one file. Copy it, you copied the memory. Which also means: back it up.

⛔ The live limit — read this before you widen the deployment

There is no caller authentication yet (tracked as B-1). Reviewer identity is proven; who is calling is not. Any orchestration that reaches the server can read and write any scope it can name, and writes are unattributed — so a bad write can't be traced or reliably cleaned. Scope isolates logically, not securely.

That's fine for one person, on one machine, over stdio. It is not fine for a second user, a network transport, a work deployment, or any client data. Those wait until B-1 closes.

For the technical reader

Under the fur

Optional detail. Everything above is the whole brief if you don't want this.

Architecture & storage
foundation
Structured on CoALA — Cognitive Architectures for Language Agents (Sumers, Yao, Narasimhan & Griffiths, Princeton; TMLR 2024; arXiv:2309.02427). The three memory types and the decision cycle come from the paper, not from taste.
storage
SQLite with sqlite-vec. Single file at ~/.memory-agent/memory.db. Schema is DDL in contracts/db/, executed as part of verification — not described in prose and hoped for.
retrieval
Reciprocal Rank Fusion over two independent searches: FTS5 keyword and sqlite-vec similarity, then weighted by recency and importance. Output is a context_block that is token-measured, not estimated, against a max_tokens you pass in.
interface
MCP over stdio. Nine tools. server.py builds its advertised schemas from contracts/mcp-tools.json rather than from Python signatures — so the contract stays the source of truth instead of drifting into decoration.
independent
A daemon runs the same CoALA cycle over the store with no host attached, consolidating and pruning on a schedule. memory-agent-daemon --once.
degradation
Only cryptography and PyYAML are hard requirements. No sqlite-vec → keyword-only recall that announces itself. No sentence-transformers → built-in hashing embedder (lexical overlap only). No tiktoken → a conservative token bound.
The nine tools
ToolWhat it does
memory_recallHybrid search across long-term memory. CoALA's retrieval action. Returns records for a program and a prose block for a prompt.
memory_rememberWrite an episodic or semantic record. The learning action, in its ungated forms.
memory_reflectConsolidate a window of memory — reasoning applied to the agent's own store. Queues, doesn't commit.
memory_propose_procedureQueue a candidate procedure. The only path into procedural memory.
memory_review_proposalsList / approve / reject. Approve and reject require an Ed25519 signature.
memory_open_cycleBegin one decision cycle, get a working-memory handle. Optional — recall-only hosts skip it.
memory_close_cycleEnd the cycle; promote working memory into durable episodic records.
memory_forgetThree escalating modes. tombstone hides but keeps — reversible. Hard delete needs explicit confirmation.
memory_statsCounts, coverage, warning signs. A memory a host can't inspect is a memory a host can't trust.
The gate, mechanically

Unapproved candidates live in a separate table — not a flag on the same row. Recall queries can't reach them even if a query is malformed, which is a structural guarantee rather than a filter someone has to remember to apply.

Approval is an Ed25519 signature over a canonical payload, and the payload is stored verbatim alongside the signature. That's what makes an approval verifiable offline years later, and what makes a post-approval edit fail the check instead of inheriting the old blessing. memory-agent verify re-checks every stored approval.

Approving is callable over MCP, and that's safe for a specific reason: the server trusts the signature, not the caller. An agent can relay an approval you produced. It cannot produce one.

Use --passphrase at keygen. The security claim is “the agent holds the tool but not the key” — and the usual deployment is an agent with shell access on the same machine as the key. An unencrypted private key at a predictable path lets it sign its own approvals, which is the exact thing the gate exists to prevent.

Verification — how you know it works
verify.py
132 contract checks — JSON Schemas validated, DDL actually executed, and the published approval signature in contracts/examples/records.json re-verified. That fixture is the golden test for the signing code.
pytest -q
One test per numbered acceptance criterion, asserting the accept: line as written, plus contract-conformance and non-functional suites.
eval_recall.py
The separate question nothing else answers: is recall any good? Scores keyword-only vs. hashing vs. sentence-transformers over one corpus, split into a lexical control set and a paraphrase set. Only the paraphrase set discriminates — an embedding that wins when the words already match has proved nothing.

If the signature check fails, suspect how the file was read before you touch the canonical form. records.json is UTF-8 with non-ASCII in it; reading it with the Windows default (cp1252) mangles a character and changes the hash — indistinguishable from canonical drift, and it invites the one repair you must never make. Editing candidate_hash() until the hashes agree would break every genuine approval.

Known limits, stated plainly
  • No caller authentication (A-3 / B-1). Blocks a work version, a second user, a network transport, and client data. Solo-on-stdio only.
  • Signing doesn't stop code execution. An attacker who can already run code and read an unencrypted key file wins. Passphrase, require_passphrase: true, or a hardware key via ssh-agent.
  • The default embedder is lexical only. HashingEmbedder catches word overlap, not meaning. Install sentence-transformers for real semantic recall.
  • Reflection's clustering is crude — by cycle, by repeated action. Tolerable precisely because it queues proposals instead of committing them (assumption A-6).
  • One file means one point of failure. Copying memory.db copies everything, which is the convenience and the risk. Back it up.

Making it actually pay off

Three habits, and the credits stop leaking

01 · Recall first

Open a session with a recall against the project's scope. One cheap call beats twenty minutes of rediscovery.

02 · Write the why

Record root causes and decisions, not status. “We chose X because Y” survives; “fixed the build” helps nobody.

03 · Clear the queue

Review proposals now and then. An unreviewed queue means reflection keeps spotting the same pattern and nothing ever becomes a playbook.

Koala fact. Of roughly 700 eucalyptus species, a koala will eat from only a few dozen. Being picky is the point — recall that returns everything is the same as recall that returns nothing.

Get it

Two commands

The second one prints the host config you paste in — key, policy, and MCP block, with the interpreter path already resolved.

# nothing to install first - venv and pip ship with Python
python -m venv ~/memory-champ-venv
~/memory-champ-venv/bin/pip install "memory-champ[recommended] @ git+https://github.com/mikeleewoodai/memory-champ"
~/memory-champ-venv/bin/memory-agent init --no-passphrase

[recommended] is literal, not a placeholder — it names an optional dependency group. On Windows the paths are Scripts\pip.exe and Scripts\memory-agent.exe. pipx and uv work too, and [all] instead of [recommended] adds semantic embeddings when lexical overlap stops being enough. Python 3.10+, MIT licensed. The README has the full setup, and the published JSON Schemas are the tool contract if you are integrating against it.

Koala fact. Koalas have two opposable thumbs on each front paw, which is what makes the grip hold. Nothing to do with the install — it is just a very good paw.
